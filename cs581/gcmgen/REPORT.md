# Does consensus-filtered GCM evidence generalise beyond proteins?

Exploration pilot, CS581 (UIUC), Fall 2026. Merge-only experiments: MAGUS's own 25 L-INS-i subset alignments
and its 10 L-INS-i backbones are fixed; only the evidence given to the Graph Clustering Merger (GCM) changes,
and every variant is paired against MAGUS's own merge (`linsi`) on the same replicate. Code: `code/`; raw rows:
`results/*.results.jsonl`, `results/*.agree.jsonl`; all tables: `results/tables.md` (generated by
`code/summarize.py`, `code/select_recipe.py`, `code/switch.py`); train/held-out protocol: `SPLIT.md`.

## 1. Question and set-up

The bbevidence and protcons pilots found that keeping only the residue pairs that a second aligner confirms
(L-INS-i ∩ FFT-NS-2 `--op 3`) improves MAGUS on proteins (BAliBASE −1.83, held-out AliSim −2.27) but is
catastrophic on hard DNA (ROSE +7 to +42), because there the second aligner is near-random. This pilot asks for
a recipe that helps on proteins **and** does not hurt DNA/RNA, with no reference and no data-type switch.

**Data** (one MAGUS draw each; 25 subsets, 10 backbones × 200 sequences, MCL + minclusters, i.e. the paper's
flags):

| type | replicates | MAGUS error % | source |
|---|---|---|---|
| protein, BAliBASE RV100 (length-filtered) | BBA0039, 0067, 0101, 0134, 0154, 0190 | 4.7–29.2 | cached MAGUS runs (worker branches) |
| protein, AliSim LG+G4 + indels (1000 taxa, 300 aa) | SIMMOD_R1, SIMMOD_R2, SIMHIGH_R1, SIMHIGH_R2 | 11.2–24.0 | regenerated here exactly per `cs581/protbench` (same seeds); fresh MAGUS draws |
| DNA, ROSE 1000 | 1000L1, L2, L3, M2, M3, M4, S1, S2, S3 (R0), 1000M2_R1, 1000L1_R1 | 1.2–11.3 | cached MAGUS runs |
| RNA | RNASim 1000 R0 and R1, 16S.M R0 | 8.9–12.9 | cached MAGUS runs |

BBA0081 and BBA0117 were dropped: their fresh MAGUS draws would have cost ~1 h each on the loaded machine.
SIMHIGH_R2's MAGUS draw failed once (disk full) and was re-run; see §6 for what finished.

**Control.** `linsi` reproduces the cached MAGUS score exactly (e.g. BBA0101 29.19, identical to bbevidence's
control), and `dup2:linsi` (every backbone twice) is identical to `linsi` on all 6 sets tested, so GCM (MCL +
minclusters) is invariant to a global scaling of the edge weights.

**Statistics.** Δ = variant − MAGUS in error points, error = (SPFN + SPFP)/2 × 100 (FastSP). W/T/L with a 0.05 tie
band; p = two-sided Wilcoxon signed-rank. Proteins and DNA/RNA are always reported separately.

**Train / held-out.** Fixed before any variant result was seen (`SPLIT.md`): training = BBA0101, 0134, 0067, 0039,
SIMMOD_R1, SIMHIGH_R1, 1000M2, 1000L1, 1000L2, 16S.M; held out = everything else. Both the adaptive-switch θ
(variant 4) and the final soft-weight/edge-support recipe were chosen on the training sets only; five extra DNA/RNA
held-out replicates (1000M4, 1000S3, 1000M2_R1, 1000L1_R1, RNASim_R1) were added after the selection and before
they were run.

## 2. Variants

All are merge-only and implemented in `code/gg.py` on top of `cs581/bbevidence/code/bbe.py`:

| name | meaning |
|---|---|
| `linsi&X` | hard intersection: per backbone, only the residue pairs that both L-INS-i and X align (bbevidence) |
| `wsoftW:linsi&X` | **soft weighting**: L-INS-i pairs that X confirms keep weight 1, unconfirmed pairs get weight W. MAGUS's edge weight is a residue-pair count summed over backbones, so this is implemented as each L-INS-i backbone at integer weight 1 plus `linsi&X` at weight 1/W − 1 (`code/run_wmerge.py`, a copy of MAGUS's `buildMatrix` loop with a per-file multiplier; checked equal to file duplication). `softW` = the same by duplicating files. |
| `linsi#esK` | **edge support**: delete every cross-subset GCM edge that fewer than K of the 10 L-INS-i backbones contribute to (protcons's `run_edgesup.py`) |
| `wsoftW:linsi&X#esK` | both: soft weights, then edge support counted over the 10 L-INS-i backbones only |
| `linsi\|cons0.7` | bbevidence's self-consistency column mask |
| second aligners X | `fftns2` (FFT-NS-2), `fftns2-op3`, `linsi-rt` (L-INS-i with shuffled input order **and** a random guide tree via `--treein`, i.e. GUIDANCE-style), `linsi-sh` (shuffled order only; dropped for cost), `ginsi`, `einsi` (`--genafpair --ep 0`), `linsi-op3`, `fftns2-nuc` (FFT-NS-2 with `--nuc` instead of `--anysymbol`) |
| `X@h`, `linsi~5` | backbones 1–5 only (cheap screen for the slow aligners), compared with `linsi~5` |

## 5. Mechanism

Two different failure modes of MAGUS's evidence, fixed by two different operations.

**(a) Low-support edges are almost all wrong, on every data type** (`code/edge_support.py`, reference used for
diagnosis only; "support" = how many of the 10 L-INS-i backbones contribute to a cross-subset GCM edge; "units"
= residue pairs, i.e. edge weight):

| rep | edges | share of edges with support < 4 | share of evidence units on them | precision of units, support 1 / 2 / 3 / ≥ 4 |
|---|---|---|---|---|
| BBA0101 | 1087771 | 0.76 | 0.114 | 0.03 / 0.07 / 0.08 / 0.76 |
| BBA0134 | 988619 | 0.85 | 0.163 | 0.02 / 0.05 / 0.08 / 0.88 |
| BBA0067 | 1283920 | 0.74 | 0.082 | 0.04 / 0.06 / 0.10 / 0.78 |
| BBA0039 | 191624 | 0.35 | 0.016 | 0.09 / 0.20 / 0.25 / 0.96 |
| SIMMOD_R1 | 253147 | 0.55 | 0.049 | 0.08 / 0.13 / 0.15 / 0.91 |
| SIMHIGH_R1 | 575607 | 0.79 | 0.139 | 0.06 / 0.15 / 0.20 / 0.84 |
| 1000M2 | 2481993 | 0.83 | 0.182 | 0.02 / 0.05 / 0.13 / 0.93 |
| 1000L1 | 2810573 | 0.84 | 0.168 | 0.01 / 0.04 / 0.08 / 0.92 |
| 1000L2 | 3352352 | 0.86 | 0.171 | 0.01 / 0.02 / 0.07 / 0.94 |
| 16S.M | 656588 | 0.45 | 0.028 | 0.12 / 0.13 / 0.22 / 0.87 |

- 45–86% of all GCM edges have support < 4, but they carry only 2–18% of the evidence weight, and only 1–25%
  of that weight is a true homology (vs 76–96% for support ≥ 4).
- Deleting them (`linsi#es4`) helps a lot on the simulated proteins (−4.1 to −5.2) and on most BAliBASE sets a
  little; on DNA/RNA it changes nothing (ΔSPFN, ΔSPFP within ±0.1). So the damage that these edges do depends on
  the data: on ROSE MCL already ignores them (their weight is tiny next to the 9–10-backbone edges), on the
  simulated proteins they chain clusters together and the gain is almost all **SPFN** (−3.5 on average), i.e.
  after the junk edges are gone MCL/minclusters can merge more true columns.
- This is the reference-free part of the recipe that needs no second aligner. It is close to the protcons
  edge-support baseline, but there K = 2–3 was only tested on proteins.

**(b) Single-backbone-precision errors that a second aligner sees.** The hard intersection with FFT-NS-2 removes
the L-INS-i pairs that FFT-NS-2 does not make. On proteins and 16S.M these unconfirmed pairs are 24–57% correct
(`prec unconf` in §4), the confirmed ones 86–97%, so filtering raises precision (ΔSPFP −2.8 on proteins). On
ROSE FFT-NS-2's own pairs are 1–18% correct and it confirms only 0.3–11% of L-INS-i's pairs, so the intersection
deletes ~99% of mostly-correct evidence (ΔSPFN +35).

**Why soft weighting is safe where the hard filter is not.** With weight w for unconfirmed pairs, an edge that
competes with a confirmed edge is down-weighted by 1/w; an edge with no confirmed competitor keeps its *relative*
weight, because MCL normalises each column (MAGUS's GCM is invariant to a global scale, §1). On ROSE almost
nothing is confirmed, so the graph is MAGUS's graph scaled by w and the result is unchanged (Δ within ±0.25 on
8 of 9 DNA/RNA sets at w = 0.03). On proteins most edges are confirmed and the unconfirmed ones lose. It is a
per-node, self-calibrating version of the switch in §4. The curve is steep: w = 0.5 and 0.25 do almost
nothing (MCL keeps any edge within a factor of 4 of the best one), w = 0.03–0.05 recovers most of the
hard-filter gain on BAliBASE, w = 0.01 starts to hurt ROSE (+0.96 on 1000M2).

**Why soft weighting alone fails on the simulated proteins.** On SIMMOD/SIMHIGH `wsoft0.03` *raises* error
(+1.1 to +3.8, all through SPFN) although the hard intersection lowers it. The down-weighted edges are still in
the graph; there they act like the low-support edges in (a). Adding the edge-support cut removes that failure:
`wsoft0.03:linsi&fftns2#es4` gets −3.7 / −3.9 / −5.1 on the simulated sets where `wsoft0.03` alone got
+1.1 / +3.8 / +1.3.

## 6. Runtime

Per-backbone cost of the second opinions (seconds of wall time per backbone, 4 backbones in parallel with 4
MAFFT threads each, on a 4-core VM that ran 3–6 lanes at once (load average 30–60), so these are inflated
upper bounds; isolated single-thread CPU from bbevidence in brackets):

| second aligner | protein s/backbone | DNA/RNA s/backbone | isolated CPU (bbevidence) |
|---|---|---|---|
| FFT-NS-2 | 2.6–15 (mean 6.3) | 15–83 (mean 43) | 1.8 s BBA0101, 14.6 s RNASim |
| FFT-NS-2 `--op 3` | 2.2–7.8 | 15–30 | 1.5 s, 14.1 s |
| L-INS-i shuffled + random tree | 1,866 (BBA0101) | 1,441–1,549 (1000M2, 1000L1) | ≈ L-INS-i: 226 s, 1,133 s |
| MAGUS's own L-INS-i backbone | — | — | 226 s BBA0101, 1,133 s RNASim |

- The selected recipe adds **one FFT-NS-2 run per backbone (~1% of MAGUS's L-INS-i backbone cost)** plus the
  intersection (≤ 3 s per replicate in Python) and nothing else.
- The merge with `run_wmerge.py` is a pure-Python graph build over 20 files (10 L-INS-i + 10 intersections),
  so merge wall time was about the same or faster than MAGUS's on proteins (fewer edges survive; e.g. SIMMOD_R1
  8.5 s vs 42 s) and 2–3× slower on ROSE (75–87 s vs 26–39 s under load). A real implementation would add
  the weights inside MAGUS's own builder in one pass.
- L-INS-i-based second opinions (random tree, G-INS-i, E-INS-i, `--op 3`) double MAGUS's backbone cost; the
  random-tree L-INS-i was also slower than plain L-INS-i (iterative refinement works harder from a bad tree).
